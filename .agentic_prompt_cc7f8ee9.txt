Title: [Lane 3] trigger.should_fire() + model_client — the decision layer

Description:
## Goal

`trigger.should_fire(utterance)` decides whether the screen shows anything at
all, correctly classifying technical questions, small talk, repeats, and
non-questions. And `model_client.fast_complete()` gives the whole project one
provider-agnostic way to call a fast model.

## Context

This is the module the judges are actually evaluating. The claim we are making
on stage is "we designed a system rather than calling an LLM," and this module
is the entire evidence for that claim. Everything else is plumbing around it.

**Build `model_client.py` first** — Lane 1 cannot start real work without it.
Keep it under about 60 lines. It exists so that swapping or adding model
providers at the event is a `.env` edit rather than a code change, which matters
because sponsor rate limits and credits sometimes arrive late or not at all.

It should also support an optional secondary provider. If `FALLBACK_MODEL_*` is
set in `.env`, retry once against it when the primary times out or errors, and
print which provider actually served the call. If it isn't set, behave exactly
as before. Two providers configured means one provider going down or rate
limiting us does not stop the demo.

Then the classifier. Four decisions, in this order:

1. **Is this a question at all?** Statements and back-channel ("mm-hmm",
   "right", "gotcha") never fire.
2. **Is it technical or spec-related?** Pricing, scheduling, and small talk
   never fire, even when phrased as questions.
3. **Have we already answered this on this call?** Re-firing the same card is
   worse than never firing — it turns the screen into noise, and the rep stops
   trusting it.
4. **Is it phrased well enough for retrieval?** If not, rewrite it into a clean
   question string in the `question` field.

Do the cheap checks before the expensive one. Decisions 1 and 3 should mostly
resolve without a model call at all, which saves latency on every line of small
talk — and most of a sales call is small talk.

## Acceptance criteria

**model_client**

1. Given `.env` sets provider, model, base URL and key, when
   `fast_complete("hi")` is called, then it returns the model's text.
2. Given the request times out or errors, when `fast_complete()` is called, then
   it returns `""` and does not raise.
3. Given `USE_MOCK = True`, then it returns a canned string with no network
   access.
4. Given the primary provider errors and a fallback is configured, when
   `fast_complete()` is called, then the fallback serves it and the provider
   used is printed.
5. Given the primary provider errors and no fallback is configured, then it
   returns `""` without retrying.

**trigger**

6. Given the utterance "Are you SOC 2 certified?", when `should_fire()` is
   called, then `fire` is True and `reason` is `"technical"`.
7. Given the utterance "How was your weekend?", when `should_fire()` is called,
   then `fire` is False and `reason` is `"smalltalk"`.
8. Given the utterance "How much does the enterprise tier cost?", when
   `should_fire()` is called, then `fire` is False — pricing is not technical.
9. Given a question already answered earlier in the same call, when it is asked
   again in different words, then `fire` is False and `reason` is `"repeat"`.
10. Given "mm-hmm", when `should_fire()` is called, then `fire` is False and
   `reason` is `"not_a_question"`, with no model call made.
11. Given the model returns malformed JSON, when `should_fire()` is called, then
   it returns EMPTY and does not raise.
12. Given a 20-sentence labelled test set, when it is run, then at least 18
    sentences classify correctly and **no small-talk sentence fires**.

## Must not

- Must not raise under any circumstance — catch and return EMPTY.
- Must not fire on pricing, scheduling, or small talk.
- Must not fire twice for the same question within one call.
- Must not make a model call for back-channel or obvious non-questions.
- Must not accept a model response wrapped in markdown fences or preamble —
  parse strictly, fail to EMPTY.

## Optimisation target — state this in the PR too

**Precision over recall.** A missed question is a small loss. A card that fires
during small talk destroys the demo and the argument behind it. Bias every
threshold accordingly, and say in a code comment exactly where that bias lives,
so it can be moved during rehearsal without hunting.

## Repeat detection

Start with the simple version: a list of answered questions for this call plus a
similarity check. Explain the tradeoff of the approach chosen.

Then, behind a `USE_MEM0` flag, show what it takes to back this with **mem0**
instead. mem0 is a hackathon sponsor and this is the one place in our system
where a real memory layer is genuinely the right tool rather than decoration.
The simple version stays as the fallback and remains the default.

## Validation

- Test: `pytest tests/test_trigger.py -q` — the 20-sentence labelled set,
  running entirely against mocks with no network access.
- The test set must include the hard cases: a technical question buried in small
  talk, the same question asked twice in different words, and a question
  addressed to the rep's colleague rather than to us.
- A debug mode that prints, per sentence, which of the four decisions stopped it
  and why. Needed for tuning, and for explaining the system on stage.

## Done when

- `model_client.py` works and Lane 1 is unblocked
- The 20-sentence test set passes at 18/20 or better
- Zero small-talk sentences fire — this is a hard gate, not a target
- The debug output makes every decision explainable in one line

- The official OpenAI Python client supports `api_key`, `base_url`, explicit `timeout`, and `max_retries`. Its current release is **2.45.0** (July 9, 2026); it retries connection errors, HTTP 408/409/429, and 5xx responses twice by default, and its default timeout is ten minutes. This feature must therefore set `timeout <= 0.4s` and `max_retries=0`, or the SDK's implicit retries can consume the classifier budget before application-level fallback runs. The issue should not pin a model ID: the model is intentionally environment-configured and available IDs vary by provider/account. [Official OpenAI Python SDK](https://github.com/openai/openai-python)
- OpenAI-compatible chat completions are a practical thin abstraction when both endpoints implement the same wire protocol. Construct one client per configured endpoint, call `chat.completions.create(...)`, and read `choices[0].message.content`; provider-specific behavior should remain confined to `model_client.py`.
- Python's `json.loads()`/`JSONDecoder.decode()` rejects trailing non-whitespace data, which satisfies the “no fences or preamble” rule. Parsing must additionally validate the exact object shape and types because syntactically valid JSON can still violate the contract. Python's decoder accepts non-standard `NaN`/`Infinity` by default, so `parse_constant` should reject them if numeric fields are ever allowed. [Python `json` documentation](https://docs.python.org/3.13/library/json.html)
- `difflib.SequenceMatcher` is lexical, not semantic. It can cheaply catch normalized duplicates and close rephrasings, but paraphrases with different vocabulary may be missed. Its score can depend on argument order and worst-case runtime is quadratic; compare short, normalized token sequences with `autojunk=False` and use a deliberately conservative, test-tuned threshold. [Python `difflib` documentation](https://docs.python.org/3.12/library/difflib.html)
- Current mem0 OSS usage installs `mem0ai`, requires Python 3.10+, initializes `Memory`, adds messages with `add(...)`, and searches with `search(query, filters={{...}})`. Defaults include an LLM, embeddings, Qdrant, and SQLite, so it is not a cheap or network-free substitute for the local list. Current Python SDK release notes show **v2.0.3** (May 26, 2026), and entity scoping belongs in `filters`; a unique call/run ID is essential to prevent cross-call repeat matches. [Mem0 Python quickstart](https://docs.mem0.ai/open-source/python-quickstart), [Mem0 releases](https://github.com/mem0ai/mem0/releases)

#### Best Practices
- Keep cheap deterministic gates first: reject empty/non-string text, known backchannels, obvious statements, and non-prospect speech where product policy requires it. Normalize with Unicode case-folding, whitespace collapse, and punctuation removal before exact-repeat comparison.
- Use one bounded primary attempt and, only on any primary failure, one bounded fallback attempt. Disable SDK retries so “once” is literal. The total primary-plus-fallback duration still needs to fit the 400 ms classifier budget; two independent 400 ms attempts would violate it.
- Treat missing/partial fallback configuration as “fallback disabled.” Log only a safe provider label, prompt length, and success; never log keys, full URLs containing credentials, prompts, or exception payloads that may echo secrets.
- Prefer precision by using deterministic deny lists/categories for pricing, scheduling, and small talk, then require an affirmative technical classification. Validate model output against an exact allow-list and fail closed to `EMPTY`.
- Separate debug detail from mandatory one-line operational output. Debug output should name the stopping stage (`question`, `domain`, `repeat`, or `rewrite`) without exposing credentials or uncontrolled model text.
- Tests should monkeypatch the SDK/client boundary and assert call counts, configured timeouts, disabled retries, fallback ordering, strict parsing, no-network mock behavior, and state isolation between calls.

#### Similar Implementations
- LiteLLM offers a unified `completion()` API and routing/fallback features, but it is a much larger dependency than the requested roughly 60-line adapter. For two OpenAI-compatible endpoints, the official OpenAI client plus a small loop better matches the repository's “plain Python/no speculative abstractions” constraint. [LiteLLM documentation](https://docs.litellm.ai/)
- mem0 provides the sponsored memory-layer alternative, while the local normalized list plus `SequenceMatcher` is the appropriate default: deterministic, fast, offline-testable, and dependency-light. mem0 should be lazily imported/initialized only when enabled and must fail back to the local implementation.

#### Security/Edge Cases
- Model output is untrusted input. Do not strip fences, search for a JSON substring, or accept a prefixed/suffixed object; parse the entire response and enforce exact keys/types/allowed reasons. Limit utterance and response sizes to avoid pathological latency/memory use.
- Prompt injection embedded in an utterance can ask the classifier to change labels or emit malformed output. Delimit the utterance as data, give a fixed schema and category rules, and fail closed. The deny rules should run outside the model where possible.
- Global repeat state can leak between tests, users, or calls, and Streamlit reruns can either unexpectedly preserve cached module state or erase plain state. A call-scoped identifier/reset mechanism is required.
- `speaker="rep"` and `"unknown"` semantics are unspecified. The validation explicitly includes a question addressed to the rep's colleague, but does not say whether that means a prospect's question should fire regardless of addressee, or a colleague/rep utterance should be suppressed.
- An empty string, whitespace, non-dict input, absent/non-string `text`, excessively long text, incomplete credentials, `None` model content, malformed response objects, mem0 import/config/search failures, and logging failures must all return the frozen empty value without raising.

### Refined Specifications
Based on the research, here are clarified requirements:
1. Preserve the frozen public signatures. Internally set the OpenAI client to `max_retries=0`; allocate explicit primary and fallback timeouts from one total budget no greater than 400 ms, and make fallback active only when all required fallback fields are non-empty.
2. `USE_MOCK` must be checked before client construction or mem0 initialization. Tests must prove zero network/client calls in mock mode. Add `FALLBACK_MODEL_PROVIDER` to `.env.example` if provider identity is required; otherwise define the printable provider as the configured model name or sanitized base-URL host.
3. Normalize short questions and keep answered questions in call-scoped state. Exact normalized equality is always a repeat; a high, clearly named `SequenceMatcher(..., autojunk=False)` threshold implements conservative fuzzy matching. Document that this favors speed and precision but may miss semantically equivalent paraphrases.
4. Use mem0 only behind `USE_MEM0=False`, lazy-load it, scope every add/search by a unique call/run filter, apply a high search-score threshold, and fall back to the local list on every mem0 failure. Do not pin mem0 merely from “latest”; pin/test the chosen release when implementation begins.
5. Accept only a complete JSON object with exactly `fire`, `question`, and `reason`; enforce boolean/string types, the reason allow-list, consistent combinations (`technical` is the only firing reason), and no markdown/preamble/trailing content. Any discrepancy returns a fresh copy of `EMPTY`.
6. The 20-case test corpus should distinguish classification accuracy from the zero-small-talk hard gate and include pricing, scheduling, backchannels, statements containing `?`, indirect/embedded technical questions, adversarial instructions, paraphrased repeats, speaker cases, malformed JSON, and call-state reset.

### Questions for Step 4 Clarification Review
1. What marks the start/end of a sales call and resets repeat memory? May the implementation add a reset helper or consume an optional call ID from the utterance, despite the frozen utterance keys?
2. When is a question added to “answered” memory? `should_fire()` only decides to fire and receives no callback confirming that retrieval produced/displayed an answer. Should it mean “previously fired,” or may another module acknowledge a successfully answered question?

### Why This Matters
Without explicit lifecycle and acknowledgment semantics, repeat state will either leak across calls or incorrectly mark questions that fired but were never answered. Timeout and provider-label answers determine whether fallback meets the latency/logging acceptance criteria, while speaker and decision-order answers change expected classifications and model-call counts.

### Alternative Approaches Considered
- **Official OpenAI client with a small endpoint loop:** Minimal code and dependencies, direct timeout/retry control, and sufficient for OpenAI-compatible providers; it does not adapt non-compatible provider schemas.
- **LiteLLM router:** Broad provider support and built-in fallback, but adds significant dependency/configuration surface for a two-provider, roughly 60-line module.
- **Local lexical similarity:** Fast, deterministic, offline, and easy to explain; misses vocabulary-changing paraphrases and needs threshold tuning.
- **Embeddings or mem0 as the default:** Better semantic recall and persistence, but adds latency, cost, external failure modes, state-cleanup concerns, and conflicts with the required simple default.

### Recommended Approach
Implement the official OpenAI-compatible client as a small, dependency-injected adapter with SDK retries disabled and one shared latency budget. Build the trigger as fail-closed deterministic gates plus one strict-JSON classification/rewrite call, with normalized call-scoped local repeat memory and optional lazily loaded mem0 using the same call scope. Resolve the six lifecycle, timeout, logging, speaker, and ordering questions in Step 4 before fixing tests or state APIs.
